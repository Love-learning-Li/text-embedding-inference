## 2. 对话中的关键演进过程

### 2.1 最初怀疑 benchmark 导致 QPS 虚高
你曾给出一版 benchmark，结果出现 **800+ QPS**，远高于历史结果。  
分析后确认核心原因是：

- benchmark 中的测试文本被改成了一个**很短的占位字符串**
- 虽然代码里写着 `context_length=1024`
- 但实际只是做了 `[:1024]` 截断
- 当源文本本身很短时，根本生成不出真正的 1024 长度输入

结论：

- 这组 **800+ QPS** 结果不可信
- 不是真实 1024 长度 workload
- 属于 **压测样本退化成超短文本** 导致的虚高

---

### 2.2 benchmark 修复：固定长度文本构造
随后对 benchmark 做了修复：

- 强制重复拼接文本直到达到目标长度
- 增加样本长度校验
- 增加 warmup
- 固定随机种子
- 增加每秒 RPS 打印
- 连接池复用，避免每请求新建 `PoolManager`

这一步解决了：

- 文本长度失真
- 客户端连接复用不当
- 冷启动干扰
- 基本统计不稳定的问题

---

### 2.3 第二个 benchmark 问题：线程先切数据，再线程内切 batch
之后又发现 benchmark 的另一个大问题：

- `_run_once()` 先按线程把 1024 条样本切开
- `_worker_thread()` 再在线程内部按 `batch_size=20` 切批

这会导致：

- 高线程下出现大量尾批次
- 例如 40 线程时，每线程只拿到约 25 条
- 每线程就变成 `20 + 5`
- 客户端实际发给服务端的是很多碎批，而不是稳定大批

结果表现为：

- `total_batches` 异常膨胀（如 56、60、81）
- 平均 batch size 下降
- GPU 很难被喂满
- 吞吐上不去，延迟反而越来越差

---

### 2.4 benchmark 再修复：全局 batch 队列版
为了解决碎批问题，又把 benchmark 改成了：

- **先全局按 `batch_size=20` 切成 batch**
- 再让多个线程从 **共享队列** 抢 batch
- 保证服务端看到的是理想的 `51*20 + 1*4 = 52` 个 batch

最终确认你实际运行的正确版 benchmark 已经满足：

- `planned_global_batches = 52`
- `total_batches = 52`
- `success_batches = 52`

这意味着：

- benchmark 侧的碎批问题已被消除
- 客户端发压模型已经基本正确
- 当前测出来的 QPS 已经是可信结果

### 3.2 tokenization-workers 的多轮实验结果

你围绕 `tokenization-workers` 做了多轮 A/B：

* `32`：更差
* `24`：`56.01 QPS`
* `20`：`58.65 QPS`（当前最好）

结论：

* `tokenization-workers` 确实影响性能

* 太高会带来争用/抖动
* 太低会供料不足

* 无法解释为什么会从预期的 **130–150** 掉到只有 **56–59**

因此：

* `tokenization-workers` 不是根本瓶颈，只是次优调节点

## 4. GPU 与服务端行为分析

### 4.1 GPU 利用率不是持续高位，而是脉冲式

你多次提供了 `nvidia-smi dmon` 输出，现象高度一致：

* `sm` 一段时间冲到 `100`
* 很快又掉到 `0 / 1 / 4 / 10 / 20`
* 然后再回到 `100`

这意味着：

* GPU 不是一直在忙
* 而是 **算一批、等一批、再算一批**
* 即 GPU 处于 **脉冲式工作**，存在明显空等

这不是“4090 算不动”，而是：

* **GPU 前面的供料链不连续**
* GPU 没有被持续喂满

---

### 4.2 RPS 日志也呈现“按 batch 跳”

benchmark 的每秒 RPS 打印也一直是这种台阶式模式：

* `20`
* `40`
* `60`
* `80`
* `100`
* `120`

而不是平滑的连续输出。

这进一步说明：

* 系统是在 **按 batch 粒度完成请求**
* batch 完成之间有明显空档
* 当前吞吐是被 **batch 完成速度** 锁死的

---

### 4.3 当前吞吐本质上由 batch_qps 决定

在当前固定配置下，典型结果是：

* `effective_qps ≈ 56–59`
* `effective_batch_qps ≈ 2.8–3.0`

平均每 batch 大约 19.69 条请求，因此：

* `2.9 × 19.69 ≈ 57`

和最终 `effective_qps` 高度一致。

这说明：

* 不是 request 数量不够
* 而是 **服务端每秒只能完成大约 3 个 batch**
* 当前瓶颈单位已经不是 request，而是 **batch 周期**

---

## 5. Token 统计结果：排除了一个重大嫌疑

为了验证输入是否“比想象中重太多”，对 benchmark 的 1024 条文本做了离线 tokenize 统计。

结果是：

* `char_length = 1024`
* `token_length min = 669`
* `token_length max = 672`
* `mean ≈ 671`
* `p95 ≈ 671`

因此在 `batch_size=20` 下：

* 总 token 量约为 `20 × 671 ≈ 13420`

而 TEI 当前配置是：

* `--max-batch-tokens = 32768`

这直接得出关键结论：

### 已明确排除的点

1. **不是被 `max-batch-tokens` 卡住了**
2. **不是因为 1024 字符文本实际重到爆炸**
3. **不是单批 token 数已经逼近 32768**
4. **当前的 20 条请求完全能放进一个正常 batch**

这让瓶颈进一步收敛到：

* TEI 服务端本身的执行路径 / 调度 / 前处理流水线

## 6. 当前已经形成的明确结论

### 6.1 已基本排除

以下因素已经不是主矛盾：

* benchmark 文本长度错误
* benchmark 碎批
* 客户端连接池问题
* `max-batch-tokens` 太小
* 输入 token 数远超预期
* `tokenization-workers` 本身是决定性根因

---

### 6.2 当前最可能的瓶颈

当前最像的瓶颈是：

1. **TEI 服务端“进入 GPU 之前”的整条供料链不连续**

   * tokenizer
   * JSON/HTTP 解析
   * batch 调度
   * 前处理
   * host → device 准备
   * 服务端执行路径固定开销

2. **GPU 没有被持续喂满**

   * 表现为 `sm` 利用率脉冲式高低切换
   * 而不是持续高位

3. **TEI 当前镜像/后端栈可能没有跑到历史最优状态**

   * 这更能解释“为什么当前只有 56–59，而你历史上认为应有 130–150”

## 7. 当前的核心矛盾

### 核心矛盾 1

**理论上 4090 在这类 workload 下你预期应达到 130–150 QPS，但当前在 benchmark 正确、batch 正确、token 数正常的前提下，仍只能稳定在 56–59 QPS。**

也就是说：

* 问题已经不在“测量方式”
* 而在“实际服务能力”

---

### 核心矛盾 2

**token 数统计表明当前 batch 仅约 13420 tokens，远低于 32768，但 GPU 仍然没有被持续打满。**

这说明：

* 不是 token 装箱不足
* 而是 **服务端流水线本身存在断续**
* GPU 经常在等，而不是一直在算

---

### 核心矛盾 3

**`tokenization-workers` 的调节只能带来小幅波动，无法解释近 2 倍以上的性能差距。**

这说明：

* tokenizer 是参与瓶颈
* 但不是主导瓶颈
* 当前真正的问题更靠近 **TEI 执行路径 / 运行栈 / 框架固定开销**

## 8. 当前亟需解决的问题

### 问题 1：历史高分环境与当前环境是否真的一致

这是当前最迫切的问题之一。必须逐项核对：

* TEI 镜像版本是否完全一致
* CUDA / 驱动 / 容器运行时是否一致
* 模型目录是否一致
* benchmark 文本和参数是否一致
* 历史上是否曾使用过不同的推理服务实现，而非当前这套 TEI

因为从现有证据看：

* 现在这次输入并不重
* benchmark 也没问题
* 但 QPS 仍远低于你记忆中的高分

这高度暗示：

* **历史高分环境与当前环境至少有一项重要差异**

---

### 问题 2：TEI 当前服务端路径到底卡在哪一段

当前最需要找出的不是“还能不能继续调 workers”，而是：

* tokenizer 是否真的在大幅拖后腿
* 还是调度/执行路径固定开销过大
* 还是当前镜像/后端对 embedding 模式不够高效

也就是说，需要进一步把瓶颈从“服务端整体”继续拆开。

---

### 问题 3：为什么 GPU 会持续出现空等

GPU 当前表现不是“满载慢”，而是“经常没活干”。

这意味着最重要的技术问题已经变成：

> **为什么 TEI 没能把已经准备好的 52 个理想 batch 连续、高效地送上 4090？**

这是当前最关键、最具体、最需要解决的问题。

---

## 9. 当前阶段的结论一句话版
